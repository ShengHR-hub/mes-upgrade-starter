# 升级版 MES 设计方案

> 数据来源：精创电子科技有限公司 MES 建设需求背景（含 7 大痛点、9 大功能需求）+
> 6 份企业数据文件（15 产品 / 13 设备 / 24 物料 / 23 账号 / BOM / 工艺路线）。
> 本方案**不走课程培训路线**，只取真实数据与业务，按"比原需求更好、更强、更完善"重做。

---

## 一、原方案的短板（为什么值得重做）

原需求文档的 9 个模块本质是"电子化纸质单据"——把 Excel/纸质搬到网页上。
它能解决"有没有系统"的问题，但解决不了"生产好不好"的问题：

1. **只记录、不决策**：有数据看板，但没有"看到异常→自动预警→给出动作"的闭环
2. **排产缺失**：工单能自动分解工序，但"哪张单先做、哪条线做"仍靠计划员拍脑袋
3. **质量只有记录**：检验录 OK/NG，但没有不良根因分析，痛点 3 的追溯只是"查得到"，不是"防得住"
4. **物料只有台账**：批次能绑定，但"要不要补货、补多少"没人算——痛点 5 只解决一半
5. **设备只有状态牌**：人工改状态，本质还是电子白板
6. **没有移动端**：操作员还得跑到电脑前报工，3 步报工的目标在 PC 端实现不了
7. **角色权限粗**：三级角色够用，但缺操作审计——出了问题查不到是谁改的数

## 二、升级版功能矩阵（痛点 → 原方案 → 升级版）

| # | 企业痛点 | 原方案做法 | 升级版做法（更强点） |
|---|---------|-----------|---------------------|
| 1 | 生产进度不透明，查单 30 分钟+ | 工单状态页查看 | **实时进度**：WebSocket 推送，订单→工单→工序三级穿透；厂长移动端首页即全局看板 |
| 2 | 工单人工分解，日 200 工序任务 | 按工艺路线自动拆工序 | **APS-lite 智能排产**：按设备状态、人员、物料齐套度自动排单，甘特图可视化，支持拖拽调整 |
| 3 | 质量追溯 1~2 天 | SN 查链路 | **全链路血缘图谱**：SN→工序→操作员→设备→物料批次→检验记录可视化；**一键导出追溯报告**（满足 IATF 16949 汽车客户审厂） |
| 4 | 报工滞后 24h、录入错 5% | 操作员网页录入 | **工位扫码 3 步报工**（扫工单→输数量→确认）；不良率超阈值**自动锁单并推送告警** |
| 5 | 物料无批次追溯 | 批次入库绑定 | **MRP-lite**：订单+BOM 自动算料，生成采购建议；低于安全库存**自动预警**；批次正反向追溯 |
| 6 | 设备状态不可见，停机 30 分钟才发现 | 人工变更状态 | **设备状态机**（运行/待机/维修/停机）+ OEE 自动计算 + 停机超时**自动告警**；预留 MQTT 接口，未来可直接接设备 PLC 数据 |
| 7 | 月报 2~3 天 | 数据看板 | **经营驾驶舱**：产量/质量/设备/交付多维钻取；**一键生成月报 PDF**；支持按车间/产线/产品对比 |

### 新增模块（原方案没有）

| 模块 | 解决什么 |
|------|---------|
| **预警中心** | 统一告警：订单延期风险、库存不足、质量异常、设备停机超时，分级推送（看板红灯/短信/企业微信预留） |
| **SPC 质量分析** | 不良品 Pareto 图、工序不良率趋势、直通率 FPY，定位"哪道工序最拖后腿"——从"记录不良"升级到"预防不良" |
| **MRP 物料需求计划** | 见上表痛点 5 |
| **移动端 PWA** | 扫码报工、扫码追溯、设备状态上报；操作员/质检员/仓库员的主力入口 |
| **开放 API** | 预留 ERP 对接、设备 IoT 对接的 REST 接口 |
| **操作审计日志** | 谁、何时、改了什么数据，全程可查（补原方案权限粗的短板） |

## 三、技术架构

### 推荐栈（务实版）

| 层 | 选型 | 理由 |
|---|------|------|
| 后端 | **NestJS (Node.js + TypeScript)** | 用户本机已有 Node 22 + MySQL 8.4，可直接跑；AI 工具链（Codex/Claude）对 TS 生态支持最好；模块化架构天生适合 MES 这种多模块系统 |
| 前端 | **Vue 3 + Element Plus** | 原方案也定 Vue3，延续；看板用 ECharts |
| 实时 | **WebSocket (Socket.io)** | 进度推送、告警推送、看板实时刷新 |
| 数据库 | **MySQL 8 + Redis** | MySQL 存业务，Redis 做看板缓存 + 告警去重 |
| 移动端 | **PWA**（一套代码，免装 App） | 操作员手机扫码即用 |
| 部署 | **Docker Compose 一键启动** | mysql + redis + backend + frontend 四个容器 |

> 备选：如果坚持课程要求，可换 Spring Boot + Vue3，数据模型与功能设计完全复用。
> 不推荐一上来就微服务——186 人企业的体量，模块化单体 + 预留 API 边界是最经济的。

### 架构图（逻辑）

```
移动端PWA ──┐
PC浏览器 ───┼──→ Nginx → 前端(Vue3) 
            │         → 后端API(NestJS) → MySQL 8
            │                        ↘ Redis(缓存/推送)
            └──→ WebSocket 实时通道（进度/告警/看板）
预留：MQTT Broker（设备IoT）/ ERP开放API
```

## 四、数据模型（基于真实数据）

主数据表（6 个 Excel 直接建表，`db/schema.sql` 已备好）：

| 表 | 来源 | 说明 |
|---|------|------|
| `product` | 01_产品清单 | 15 个产品型号，含产品线/月产量/标准工时 |
| `device` | 02_设备清单 | 13 台设备，含车间/产线/状态/购买年份 |
| `material` | 06_物料清单 | 24 种物料，含类别/安全库存/供应商 |
| `bom` | 03_BOM清单 | 2 个产品 BOM（18+12 行），层级+用量 |
| `process_route` | 04_工艺路线 | 15 条路线总览 + JC-PLC-2001 的 10 道工序详情 |
| `sys_user` | 05_人员账号 | 23 个账号，admin/manager/operator 三级角色 |

业务表（支撑升级功能，同样在 schema.sql 中）：

| 表 | 用途 |
|---|------|
| `sale_order` | 销售订单（痛点1的源头） |
| `work_order` | 生产工单（状态机：待启动→在产→完工） |
| `work_task` | 工序任务（工单自动分解 + APS 排产结果） |
| `report` | 工序报工（良品/不良品数） |
| `qc_record` / `defect` | 检验记录 / 不良品记录（SPC 分析源） |
| `material_batch` | 物料批次（入库批次号，绑定产品 SN） |
| `sn_trace` | SN 全链路追溯（工序+操作员+设备+批次+检验） |
| `equipment_log` | 设备状态变更日志（OEE 计算源） |
| `alert` | 预警记录（预警中心） |
| `audit_log` | 操作审计 |

种子数据：`db/seed_from_excel.py` 一键把 6 个 Excel 转成 `seed.sql`，
系统起来立刻有 15 产品/13 设备/24 物料/23 账号的演示环境。

| 阶段 | 内容 | 对应痛点 |
|------|------|---------|
| **M1 数据层** | 建表 + Excel 种子数据导入 + 基础 CRUD | —（地基） |

## 六、AI 集成方案（适应市场）

> 结论：可以接，而且应该接。"MES + AI" 比纯 MES 更符合当前市场（新型工业化政策风口、
> 工业 AI Agent 落地），也对得上课程"AI重构"的主题。但要分两层做——**不是所有 AI 功能
> 第一天都能用**，预测类功能需要系统先跑起来积累历史数据。

### 6.1 现在就能做的（基于现有主数据 + LLM）

| AI 功能 | 解决什么 | 技术实现 |
|---------|---------|---------|
| **厂长智能问数** | 厂长不用学报表，手机上问"上周哪条产线直通率最低？"直接得答案 | Text-to-SQL：LLM 把自然语言转成 SQL 查业务库，结果再转成中文回答；演示效果最强 |
| **工艺知识问答** | 操作员/质检员问"JC-PLC-2001 第 5 道工序注意什么？" | RAG：把工艺路线、BOM、需求背景文档向量化检索后回答 |
| **AI 生产日报** | 痛点 7 的"写报告"部分自动化 | 定时任务拉取当日数据 → LLM 生成文字总结 → 推送 |
| **预警根因分析** | 告警不只响，还告诉你"可能是什么原因" | 告警触发时，LLM 结合关联数据（同批次物料/同设备/同操作员）给出根因假设和处置建议 |

### 6.2 跑起来攒数据后做的（需要历史时序数据）

| AI 功能 | 前提数据 | 说明 |
|---------|---------|------|
| 工序不良率异常检测 | 连续 4~8 周的报工/检验记录 | 初期用统计规则（3σ），数据量够了上 ML 模型 |
| 质量预测 | 历史检验 + 工艺参数 | 预测某工单的不良风险，提前干预 |
| 智能排产优化 | 历史工单 + 设备状态 + 交付记录 | 从规则排产（APS-lite）升级到优化算法 |
| 订单需求预测 | 6~12 个月历史订单 | 指导备料和产能规划 |

### 6.3 架构增量（在原架构上加两块）

```
原有：前端(Vue3) → 后端API(NestJS) → MySQL/Redis
新增：
  ai-gateway 服务 ─ 统一 LLM 调用（OpenAI 兼容接口，可接中转站/本地模型）
                    ├─ prompt 模板管理
                    ├─ token 用量与成本统计（ai_query_log 表）
                    └─ 开关：未配置 Key 时 AI 功能自动降级，系统照常跑
  agent 编排 ─ 简单场景用 function calling（如问数），复杂用小流程
```

- 新增表 `ai_query_log`（见 schema.sql）：记录每次 AI 问答的问题、生成的 SQL、
  token 消耗——既是审计，也是成本账本
- RAG 知识库：pgvector 或轻量向量库二选一，初期数据量小，用 SQLite+向量扩展都够

### 6.4 成本与诚实说明

- 厂长问数、日报生成这类**低频场景**，token 消耗极小，走现有 API 中转站每月几块钱量级
- RAG 问答 embedding 一次生成、重复使用，成本可忽略
- **不建议**一上来就做"大模型直连设备"之类重方案——186 人企业的真实需求是"好用、稳定、便宜"

### 6.5 对个人的市场价值

- 求职：简历上从"做了个 MES"变成"做了个 AI+MES（Text-to-SQL 问数、RAG 知识库、智能预警）"，
  直接对口 AI Agent / AI 应用开发岗位
- 课程：名字就叫 AI 重构，AI 功能是天然的加分项
- 企业侧：同等报价下，"带 AI 助手" 的方案比纯 MES 更有竞争力

## 七、一句话总结

原方案是"**把纸质单据搬进电脑**"（记录系统）；
升级版是"**让数据自己干活**"——自动排产、自动预警、自动算料、自动追溯（决策系统）。
同一批真实数据，前者只做到"查得到"，后者做到"防得住、算得准、看得清"。
