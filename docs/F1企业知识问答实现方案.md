# F1 企业知识问答（RAG）实现方案

> 状态：**已实施并验证**（2026-10-16，经项目所有者「全部授权」）。实现：ai-service `GET /api/v1/ai/knowledge-sources`；backend `modules/knowledge/`（代理+审计+7 例单测）；frontend `AiKnowledgeView.vue`。验证：真实 Chrome 浏览器问答/拒答/来源清单实测通过（见 `docs/S12真实环境验证报告.md` §A27-A31、§A37）。
> 核心事实：AI 服务侧能力**已具备**（`/api/v1/ai/rag-answers` + rag.py 检索引擎 + knowledge.json 31 块）；
> 缺失的是外部契约层（NestJS 代理 + knowledge-sources + 前端页面）。

知识库现状（`ai-service/knowledge.json`）：31 块，来源 = 需求背景文档（19 块，含七大痛点/九大功能总览）+ 企业数据（12 块：产品/设备/物料/人员/BOM×2/工艺路线）。每块结构：`{source, text}`。检索参数：minScore=0.12、minResidue=2（见 /health 回显）。

## 2. 知识库数据结构

沿用现有 `{source, text}` 结构并扩展字段（向后兼容）：

```json
{
  "source": "02_设备清单.xlsx",
  "chunkId": "device-006",
  "docType": "enterprise-excel | requirement-doc",
  "text": "...",
  "tags": ["设备", "SMT-2线", "维修中"]
}
```

- `chunkId` 满足契约 citations 的 `chunkId` 字段（当前缺失，需补）
- `docType` 用于「企业文档 vs 需求文档」来源区分展示
- knowledge-sources 的聚合口径：按 `source` 分组统计 chunkCount（契约明示「实际以 knowledge.json 统计」）

## 3. Excel/文档导入方式

复用 `ai-demo/build_kb.py` 的既有模式（已验证可生成 knowledge.json）：

- 输入：`data/01-06_*.xlsx`（6 份企业 Excel）+ 需求背景文档文本
- 输出：`ai-service/knowledge.json`（重建时保留版本备份，diff 审查后替换）
- 触发方式：手动脚本执行（`python build_kb.py`），不提供运行时上传（避免知识库被随意篡改；如需在线导入另立需求）
- 增量策略：按 source 名覆盖更新对应块，其余不动

## 4. 检索方式（复用现有引擎，不重写）

- `ai-service/rag.py` Retriever：分词 + 词项重叠打分，`minScore=0.12` 判定「有依据」，未覆盖片段长度 `minResidue=2` 判定「无依据」
- 接入商业模型时（AI_BASE_URL + AI_API_KEY 已配置）：检索结果作为上下文交给 LLM 组织答案，**引用与数字不得由 LLM 改写**（沿用 F2/F3 的「LLM 润色不改指标」口径）
- 未配置模型：local 模式直接基于检索文本作答，`mode=local` 如实标注

## 5. 引用来源格式（契约 §122 示例）

```json
"citations": [{"sourceName": "02_设备清单.xlsx", "chunkId": "device-006", "relevance": 1}]
```

- sourceName = knowledge.json 的 source；chunkId = 扩展后的块 ID；relevance = 检索分（0-1）
- 前端逐条展示来源名 + 相关度，点击可展开原文片段

## 6. 超纲问题拒答

- 检索无依据（低于 minScore 或未覆盖）→ `answerStatus: "no_evidence"`，answer 明确「资料中没有该信息」，citations 为空
- 问题命中业务数据类意图（产量/工单等）→ 引导至 F3 问数，不编造
- 拒答文案模板集中在 rag.py 现有 `_rag_evidence_problem` 逻辑中扩展

## 7. 权限控制（契约 §5）

- POST /api/v1/rag-answers：admin / manager / operator 三角色均可用
- GET /api/v1/knowledge-sources：三角色均可用
- 沿用 NestJS `permission-matrix.ts` 登记权限码 `rag-answers:create` / `knowledge-sources:read`（前端 config 已预留该权限码）

## 8. 实现步骤（严格按现有 API 契约，不自改接口）

1. **AI 服务**：新增 `GET /api/v1/ai/knowledge-sources`（内部，带服务令牌；按 source 聚合 chunkCount，分页）；rag-answers 补 chunkId 字段
2. **NestJS**：新增 `modules/knowledge/`（controllers：rag-answers POST 代理、knowledge-sources GET 代理），复用现有 `ai-proxy.service.ts` 模式（注入 AI_SERVICE_TOKEN、错误码映射、DTO 校验：question 1-500 字、topK 1-5 默认 3）
3. **前端**：`views/ai-knowledge/AiKnowledgeView.vue` 接入 modules.ts（implemented: true）；问答表单 + 答案区 + 引用列表 + 来源管理页
4. **测试**：
   - 单测：检索打分、拒答边界（超纲/业务数据类/正常）
   - e2e：三角色分别调用 rag-answers（operator 可问、knowledge-sources 可读）；不带令牌 401；topK 越界 10001
   - 契约一致性：响应字段与 api-contract.md §F1 逐字段比对
5. **验收**：真实 AI 服务（local 模式即可）+ 真实浏览器提问「回流焊炉加热区故障怎么办」等场景，核对引用来源
