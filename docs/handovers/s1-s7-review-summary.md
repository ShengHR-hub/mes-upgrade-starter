# S1-S7 独立审查与返修收益总结

> 项目：精创电子 MES + AI
>
> 审查角色：独立技术总控
>
> 适用范围：代码复审、后续开发放行、隔离测试边界
>
> 不等同于：完整业务验收、真实生产验收或上线批准

## 1. 总体结论

从 S1 到当前，项目已经从“功能代码完成”逐步提升为“有统一契约、有业务边界、有错误防护、有独立验证记录”的全栈系统。

S0-S6 已按阶段结论通过，允许继续后续开发及获授权的隔离测试。S7 多轮返修后，主要业务逻辑问题已得到修正，但最近复审仍发现一项事务异常处理问题：指定隔离级别或事务内查询失败时，代码会捕获异常并使用默认隔离级别重跑，可能掩盖真实错误并降低一致性保障。

因此，当前结论是：

- S1-S6：代码层面已具备继续开发基础。
- S7：大部分返修已完成，仍需修复事务异常降级重跑后再宣布代码复审通过。
- 真实 MySQL 多表事务、并发隔离、真实 JWT 三角色登录和浏览器闭环尚未完成独立验收。
- 不因真实认证尚未完成而全面禁止后续开发，但不能将认证、数据库事务或浏览器闭环称为已验收。

## 2. 各阶段审查带来的变化

### S1：统一基础约束

审查重点是 API 契约、需求边界、数据库表结构和阶段安排。项目冻结了 18 张表，并要求 `synchronize=false`，明确了前后端接口路径、统一响应结构、错误码、权限矩阵和演示数据边界。

带来的收益：

- 前后端依据同一契约开发，减少字段、状态和错误处理不一致。
- 数据库结构不再由 ORM 自动改写，降低误改表和环境漂移风险。
- 后续审查可以按已批准规则判断，不把模型建议误当成业务批准。

### S2：后端骨架

后端逐步统一了响应包装、参数校验、异常映射、认证守卫、角色守卫、请求标识和日志脱敏。未认证请求采用 fail-closed 处理，业务接口不开放匿名写入。

带来的收益：

- 参数错误、权限错误、资源不存在和能力未启用能够稳定区分。
- 前端可以按统一 `code` 和 HTTP 状态处理错误。
- 日志不会直接输出密码、密钥、完整令牌或数据库凭据。

限制：真实 JWT 登录、Argon2id 密码哈希和三角色登录闭环仍未独立验收。

### S3-S4：前端基础与页面骨架

前端建立了统一 HTTP 服务适配、响应完整性校验、请求取消、异步任务轮次隔离、详情流程隔离和提交防抖。预览默认关闭，生产路径不能绕过登录；演示数据明确标注来源。

带来的收益：

- 快速切换页面或查询条件时，旧请求不容易覆盖新结果。
- 不完整响应不会被误当成正常业务数据；合法的 `data:null` 可以正常处理。
- 重复点击、取消和失败重试的界面行为更加可控。
- 演示数据不会被误称为真实生产数据。

### S5：订单与工单

订单确认、工单生成、列表索引和工单状态逻辑经过多轮审查。修复了提交锁时机、旧索引污染、分页完整性、并发隔离、BIGINT ID处理、日志脱敏和写请求自动重试等问题。

已落实的关键规则包括：

- 生成工单时 `planStart/planEnd` 保持 `null`，不擅自推断计划。
- 大整数 ID 以字符串传递，并检查有符号 BIGINT 上限。
- 写请求不自动重试，避免网络异常造成重复业务写入。
- 旧任务和旧索引立即失效，避免切换订单后显示旧数据。
- 提交 guard 在任何异步等待之前加锁。

带来的收益：

- 重复确认、重复提交和旧列表污染风险降低。
- 前后端不会因 JavaScript 数字精度损坏数据库主键。
- 订单和工单状态更容易追踪，后续页面查询结果更稳定。

### S6：生产报工与质量检验

S6 对 B3 生产报工和 B4 质量检验进行了三轮独立审查。初始发现的构建错误、认证守卫缺失、异步重复提交、查询参数嵌套、日期边界、时间偏移、ID和数量校验、错误吞咽、固定不良原因以及测试证据不足等问题已整改。

最终确认的关键规则包括：

- 工单允许暂停、恢复和关闭，完工和关闭为终态，不能重开。
- 后续任务开工前，所有更小 `seq` 任务必须完工。
- 任务和工单人工确认完工，报工达到计划数量不自动完工。
- 设备状态、产线匹配、操作员 enabled 状态和车间范围必须完整校验。
- 修改后的完整分配结果必须重新校验，不能只检查本次提交字段。
- 报工和质检事务统一先锁工单，再锁任务。

带来的收益：

- 报工和质检更符合批准的生产流程，减少越序开工和非法分配。
- 并发更新时的锁顺序更加一致，已知的交叉锁顺序风险降低。
- 数量、时间、ID和错误响应更可靠。

### S7：经营驾驶舱与预警中心

S7 主要涉及 B8 驾驶舱、B10 预警中心、生产指标、质量指标、交付预警和看板钻取。经过多轮返修，以下问题已经关闭：

- 历史查询采用严格半开区间，排除次日零点记录。
- 缺失或逆序计划不会直接造成 500；会返回数据不足状态。
- 阈值使用原始数量计算，不因显示四舍五入漏报。
- 缺计划时不生成基于局部数据的交付预警。
- Q6 未批准前，预警状态写入由服务端返回 `422/30006` 拦截，前端入口关闭。
- 报工、质检和工单钻取会传递产线、车间和产品条件。
- 路由条件被移除时，目标页会清空旧筛选并重置分页。
- “未分配”筛选支持 NULL、空值和明确的未分配标识。
- 新增筛选字段具备字符串和长度校验，数组、空值和超长输入在查询前拒绝。
- 工单筛选按末道任务的产线和车间归属，不再使用任意工序扩大范围。
- 缺计划检查、候选工单、窗口报工和累计良品读取进入同一事务执行器。

带来的收益：

- 看板数字、预警数字和明细查询更容易保持同一口径。
- 例如“昨日完成 50 件、今日完成 26 件”时，累计完成量保持为 76 件，不会被当日产量覆盖。
- 点击某条产线后，明细范围更能解释看板指标，减少“看板和明细对不上”。
- 未批准的预警写操作不会被界面误导为可用功能。
- AI 日报、问数和规则评估可以复用同一聚合服务，减少各模块自行计算造成的数字分叉。

## 3. 当前尚未关闭的问题

### P2：事务异常被静默降级重跑

文件：`backend/src/modules/dashboards/metrics-aggregation.service.ts`，事务封装的异常处理位置。

当前代码在指定 `REPEATABLE READ` 事务启动失败，或事务内部查询失败时，会捕获任意异常，然后使用未指定隔离级别的默认事务再次执行。这样可能出现：

- 第一次失败原因被隐藏。
- 第二次运行使用数据库默认隔离级别，不能保证原本要求的一致性。
- 最终请求返回成功指标，但调用方不知道已经发生降级重跑。

建议直接让异常向上传播；若未来需要重试，必须限定异常类型、保持明确隔离级别并记录可审计原因。

## 4. 当前验证层级

已完成或多次执行：

- 后端单元测试、无数据库 HTTP 测试、Lint、NestJS 构建和完整 TypeScript 检查。
- 前端单元测试、类型检查和生产构建。
- 实际 SFC setup 逻辑探针。
- 实际 NestJS 控制器、守卫、DTO 和 SQL 生成路径探针。
- 文件完整性和凭据模式扫描。

仍未完成：

- 真实 MySQL 多表事务回滚和并发累计验证。
- 真实 `REPEATABLE READ` 多连接隔离验证。
- 真实 HS256 JWT 登录、停用账号和角色变化即时生效验证。
- 真实浏览器 DOM、Chrome/Edge 交互及页面闭环验证。
- 完整业务验收、生产数据验收和上线批准。

## 5. 对后续开发的意义

当前可以继续开展不依赖真实认证和真实数据库写入的后续开发、单元测试、静态检查和授权的隔离测试。后续 S8/S9 开发可以复用 S7 的聚合服务，但必须保留：

- `doneQty` 与窗口产量的区分。
- 末道任务归属规则。
- 缺失数据的诚实状态表达。
- `snapshotAt` 截止时刻。
- 统一权限和演示数据标识。

在事务异常降级问题修复并重新验证前，不应把 S7 宣布为代码复审通过，更不能据此宣布完整业务验收或上线。

## 6. 证据使用原则

- 执行方自测只能证明命令在其环境中通过，不能替代独立复审。
- 测试替身只能证明控制流、参数和 SQL 生成，不能替代真实数据库行为。
- SFC setup 测试不能替代浏览器 DOM 和真实用户交互。
- 截图和模型建议不能作为独立实测证据。
- “允许继续开发”不等于“业务验收通过”。
